# @customs/db

Supabase migrations, generated database types, and the zod schemas shared by the API
(`apps/web/app/api`), the companion and the Discord bot.

```
supabase/config.toml        local stack config (project_id "customs-night")
supabase/migrations/        numbered SQL. Never edit one that has been applied; add a new file.
src/schemas/                zod schemas for every boundary. Imported by web, companion, discord.
src/rosterKey.ts            splits.roster_key: sorted puuids, the "same ten people" key.
src/localStack.ts           test-only: finds the CLI local stack. The app never imports it.
src/types.ts                GENERATED by `pnpm db:types`. Do not hand-edit.
```

## Local stack

Tests and local development run against the Supabase CLI local stack, so nothing needs the hosted
project. Docker must be running.

```
pnpm db:start     # supabase start  -> prints the local API URL and keys (also: supabase status -o env)
pnpm db:reset     # supabase db reset -> drops the database and replays every migration
pnpm db:stop      # supabase stop
pnpm db:types     # regenerate src/types.ts from the LOCAL stack
```

`supabase status -o env` prints `API_URL`, `ANON_KEY` and `SERVICE_ROLE_KEY`. Put them in
`apps/web/.env.local` (see `.env.example`). They are the same on every machine and are not
secrets, but they still do not belong in the repo.

Storage is disabled in `config.toml`: we store no files, and the Storage container's restart made
`supabase db reset` exit non-zero on this machine. Everything else (Auth, Realtime, Studio) is on.

The first `supabase start` pulls ~5 GB of images; `supabase/postgres` alone is ~900 MB. On a slow
link, pull it on its own first: `docker pull public.ecr.aws/supabase/postgres:<tag>`, where the tag
comes from `supabase services`.

## The hosted project

There is no hosted project yet. Once someone creates one, per machine, once:

```
supabase login                                # opens a browser, stores an access token
supabase link --project-ref <ref>             # run from packages/db; <ref> is in the project URL
pnpm db:migrate                               # supabase db push: applies pending migrations
```

`db push` only ever applies migrations that the hosted `supabase_migrations.schema_migrations`
table has not seen. It never diffs and never drops. After it succeeds, run `pnpm db:types` against
the local stack (they are the same migrations) and commit the result.

## Writing a migration

```
supabase migration new <name>     # supabase/migrations/<timestamp>_<name>.sql
pnpm db:reset                     # apply everything from scratch, locally
pnpm db:types                     # regenerate src/types.ts
pnpm --filter @customs/db test    # schema tests run against the local stack
```

Rules:

- **Never edit a migration that has been applied** anywhere but your own machine. Add a new
  numbered file. `0001_init.sql` is applied; it is frozen.
- Every new table gets RLS in the same migration that creates it, plus the DML revoke: Supabase
  grants `anon` and `authenticated` insert/update/delete on every new table in `public` by
  default, and that default applies to your table too.
- A table the tonight page or the bot subscribes to must be added to the `supabase_realtime`
  publication in the same migration. A table that is not published never emits, silently.
- Regenerate types after every migration and commit the result.

## What 0001_init.sql sets up

- Every table from `docs/01-architecture.md` "Data model", keyed by PUUID, with the idempotency
  keys the ingest relies on: `players.puuid`, `lobbies.lcu_party_id`, `games.lcu_game_id` unique.
- Postgres enums for the unions `packages/core` declares (`lobby_status`, `player_role`,
  `game_source`, `companion_command_kind`, `companion_command_status`), so the generated types are
  string unions rather than `string`. `side` is a smallint checked against 100/200.
- `ratings.ordinal` is a stored generated column (`mu - 2 * sigma`) with an index on
  `(season_id, ordinal desc)` for the leaderboard.
- Season 1, active, with a fixed id (`SEASON_ONE_ID`), so ratings and games always have a season.
  `games.season_id` defaults to `public.active_season_id()`.
- `public.bootstrap_admin(puuid)`: insert-or-promote the first admin, idempotent, service role
  only. The API calls it on start with `BOOTSTRAP_ADMIN_PUUID` (a migration cannot read the
  deployment environment).
- `updated_at` triggers on `lobbies`, `ratings` and `discord_config`.
- `lobbies`, `lobby_members`, `splits`, `games`, `game_players` and `ratings` are in the
  `supabase_realtime` publication, which is what the tonight page (M3.4) and the bot (M4.4)
  subscribe to. `players` is not: it is not publicly readable.

## Reading data: RLS

- **Public (anon and authenticated) read:** `seasons`, `ratings`, `lobbies`, `lobby_members`,
  `splits`, `games`, `game_players`, and the `players_public` view.
- **`players` itself is service-role only.** It holds `discord_id`. The web client, the bot and
  anything anonymous must select from `players_public`, which is the same table without that
  column. Asking for `discord_id` anywhere else is `401 permission denied`.
- **No public read at all:** `companion_tokens`, `companion_commands`, `discord_config`.
- **No anon or authenticated writes anywhere.** There is not a single insert/update/delete policy;
  the DML grants are revoked as well. The API writes with the service role key, which bypasses RLS,
  so every write goes through a route handler that has already checked the companion token.
- Admin session policies land with M1.6; `0001_init.sql` marks the spot.

## Tests

`pnpm --filter @customs/db test` runs two kinds:

- pure schema tests (`src/schemas/*.test.ts`, `src/rosterKey.test.ts`) — always run;
- `src/schema.integration.test.ts` — talks to the local stack through PostgREST and checks the
  unique constraints, the enum and check constraints, the RLS boundary and `bootstrap_admin`.
  It **skips itself** when the stack is not reachable, so `pnpm -r test` is green without Docker.
  It namespaces every row it creates with a run id and deletes them afterwards.
