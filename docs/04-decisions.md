# Decisions

Append-only. One row per decision that the code or docs would otherwise leave ambiguous. Newest at the bottom.

| Date | Decision | Why | Alternatives rejected |
|---|---|---|---|
| 2026-09-08 | Build our own instead of using In-House Queue | Existing bots need manual reporting and equal-start ratings; we want zero-input and rank seeding. | In-House Queue (free, good baseline, still the fallback), MatchBalancer ($5.99/mo, no Discord) |
| 2026-09-08 | Companion app is phase 1, not a later add-on | It is the only way to get results and rosters without a human step, and it replaces the Riot public API. | Manual `/result` command with vote confirmation |
| 2026-09-08 | Supabase for database, auth, realtime | Hosted Postgres with the rest included; Discord OAuth is a checkbox. | Bare Postgres on Neon plus separate auth and pub/sub |
| 2026-09-08 | API lives in Next.js route handlers, not Supabase edge functions | One runtime and deploy; `packages/core` imports cleanly. | Edge functions (Deno toolchain), separate Fastify service |
| 2026-09-08 | Companion is a Node CLI packaged as an exe; tray wrapper deferred to M6 | Keeps the project all TypeScript, shares `packages/lcu`. | Tauri or Electron from day one, Overwolf |
| 2026-09-08 | Players keyed by PUUID; Discord link optional and admin-managed | Riot IDs are renamable; balancing and stats need no Discord identity. | Require Discord OAuth before playing |
| 2026-09-08 | No check-in. Roster comes from the custom lobby | The lobby is the truth about who is playing. A check-in is a form people skip. | Discord button check-in, web check-in as the primary flow |
| 2026-09-08 | Discord webhook in M3, bot process only in M4 for voice | Posting needs no process; voice moves do. | Full bot from the start |
| 2026-09-08 | OpenSkill for ratings, balance on mu, leaderboard on mu - 2 sigma, display mu * 60 | Team-aware rating with uncertainty; display scale reads like familiar MMR numbers. | Elo, Glicko-2 per player, raw TrueSkill port |
| 2026-09-08 | Role multipliers 1.00 / 0.93 / 0.85 for main / secondary / fill | Simple, explainable, tunable in one constant with tests. | Per-role ratings (too sparse for our game count) |
| 2026-09-08 | Backfill (M5) is the recovery path for missed games, never manual entry | Keeps ratings honest; manual entry invites disputes. | Admin manual result entry |
| 2026-09-08 | Workspace packages are `@customs/*`; apps keep bare names (`web`, `companion`, `discord`) | One prefix, no collision with npm, and `pnpm --filter web dev` stays exactly as CLAUDE.md documents it. | `@customs-night/*` (long), unscoped `core`/`db` (collides with real packages) |
| 2026-09-08 | Workspace packages ship TypeScript source: `main`, `types` and `exports` all point at `src/`, and no package emits anything | No build step to forget before `dev`, `test`, `typecheck` or a Vercel deploy; every consumer types from source. vitest and Turbopack transform the source directly, `transpilePackages` in `next.config.ts` covers the Next side. | Building each package to `dist` first (an extra step in front of every command, and a broken `next build` on a fresh checkout) |
| 2026-09-08 | Typecheck is a plain `tsc --noEmit` per package, no composite projects and no TypeScript project references | References only pay off when consumers read `.d.ts` from `dist`, and we type from source instead. With references and `types` pointing at `dist`, a fresh checkout failed `next build` with TS6305 before anything had been built, which is exactly the Vercel case. `pnpm -r` already runs packages in dependency order. `apps/web` runs `next typegen && tsc --noEmit`. | Composite projects + `tsc -b` emitting declarations into `dist/` (rejected: broke `next build` on a fresh checkout) |
| 2026-09-08 | TypeScript pinned to 5.9.x, not the 7.0 native port | Next 16, Biome and vitest are proven on 5.9 today; a foundation task is the wrong place to absorb a compiler rewrite. Revisit once the toolchain has shipped 7.x support. | TypeScript 7.0 (current `latest`) |
| 2026-09-08 | One vitest config per package, no root workspace/projects file | `pnpm -r test` already runs every package in dependency order, each with its own environment; the workspace file has moved twice in three vitest majors. | Root `vitest.workspace.ts`, root `test.projects` |
| 2026-09-08 | `next.config.ts` sets `agentRules: false` | Next 16 writes its own `AGENTS.md` and `CLAUDE.md` into `apps/web` on first dev run. Agent instructions for this repo live in the root `CLAUDE.md` and `docs/`; a second generated set would compete with them. | Let Next generate them and commit them |
| 2026-09-08 | The M1.4 worked example uses settled `mu` values, not raw seeds | Seeds are multiples of 0.25, so any seed-only roster has a gap that is a multiple of 15 display points; the accepted criterion "gap of 100" is unreachable from seeds alone. Ten friends a few weeks into a season have drifted `mu` anyway, so the example is also the more honest picture. Criterion left unchanged. | Softening the criterion to "gap of at most 100" or moving it to 105; both hide the real constraint |
| 2026-09-08 | The worked example's three splits are all-main with gaps 100, 170 and 220 | Any split with someone off-role costs at least 240 (2 x 120) before its gap counts, so keeping all three under 240 makes the top three stable and the test deterministic without a tie-break. `01-architecture.md`'s sample string "gap 300" stays as a format illustration only. | Designing for a 300-point next best; every candidate roster then let an off-role split into the top three |
| 2026-09-08 | Players are sorted by PUUID before enumeration, and the lowest PUUID is always on blue | Makes output byte-identical for the same ten in any order, fixes side colour without an extra rule, and still lets red be the favoured side. | Blue is always the stronger side (then "Red favored" never prints); input order decides (not reproducible) |
| 2026-09-08 | `gap` and `score` are computed on effective (role-adjusted) skill in display units; `gap` is rounded once for display | Keeps `score = gap + penalties` true, so the explanation's number is the number that chose the teams. | Gap on raw `mu` (then the printed gap does not match the decision) |
| 2026-09-08 | A `roleOverride` becomes the main; the player's usual main becomes their secondary; the declared secondary drops to fill | One sentence to a friend: "the role you tapped is your role tonight, your usual role is your backup." Never treats someone's real main as a random fill. | Override replaces the main outright (punishes the player if the balancer needs them elsewhere) |
| 2026-09-08 | A player with no known main role is flexible: every role is a main and they are never counted off-role | A new face must not make the night worse or produce a misleading "1 off-role" line before anyone has set their roles. | Treat unknown roles as fill on everything (constant penalty, misleading explanation); refuse to balance until an admin sets roles (a manual step, against the whole product) |
| 2026-09-08 | Duo locks are a filter, not a penalty; if no 5/5 partition satisfies them, `balance` throws | An "infinite penalty" number is a footgun in float arithmetic. Throwing with the blocks named lets the API tell the group which duo to drop. | Infinite penalty constant; silently dropping the duo that does not fit |
| 2026-09-08 | The repeat-split penalty matches the same five people on either side, colour-agnostic | Swapping blue and red is not a different night to the people playing. | Comparing blue to blue only |
| 2026-09-08 | Explanation wording: numerals throughout, "N off-role: Name at role", "Next best: swap A and B" for one change and "N swaps" for more, next-best off-role count appended when it differs, clause omitted when there is no next split | Discord-length, friend-toned, and it stops the "next best has a smaller gap" line from reading as a bug. | "Omar on secondary (jungle)" (jargon); spelled-out numbers (inconsistent with "Gap 100") |
| 2026-09-08 | `rateGame` has no draw path; `winningSide` is `100` or `200` | A League custom cannot draw, and a remake is not a game — the API drops it before rating. | Modelling draws for completeness |
| 2026-09-08 | Workspace dependency direction is one-way: `core` depends on no workspace package; `db` depends on `core`; `web` depends on `core` and `db`; nothing may import into `core` | Keeps `core` pure and testable with no I/O anywhere near it, and keeps the import graph acyclic so a package can be reasoned about alone. `lcu` is imported only by `apps/companion`; the web app must never import it. | `core` importing schemas from `db` (would drag zod and the database shape into the pure layer) |
| 2026-09-08 | `lastSplit` is the most recent chosen split whose lobby had the same ten players, else null | The repeat penalty exists to stop "same teams as last time" for the people in the room; a split from a lobby with a different roster is not the same night and would penalise teams nobody has played. Same ten in a different order still counts, since the lobby is a set of puuids. Derived by the API (M2.7), never by core. | Always the previous chosen split whatever the roster (penalises unrelated teams); the previous split of the same lobby row only (rebalance after a member change would wipe the memory); a time window such as "tonight" (an arbitrary clock rule in a pure-ish path) |
| 2026-09-08 | The sample explanation string in `01-architecture.md` is the worked example's split 1, verbatim | Two different sample strings in two docs is how a doc goes stale unnoticed; the architecture doc now shows the string the tests pin (M1.4). Supersedes the earlier row that kept "gap 300" as a format illustration. | Leaving "gap 300" with a footnote (already caused one question); dropping the sample from the architecture doc (the format is worth showing where the balancer is described) |
| 2026-09-08 | `seedFromRank` matches tier and division case-insensitively; a missing or unrecognised division on a ranked tier (`null`, `'NA'`, `'V'`) seeds at the tier base (IV) | The client sends uppercase, but the value passes through the companion and the database on the way here; a casing slip must not seed a whole night at 20. "Your division was unreadable so you start at the bottom of your tier" is one sentence to a friend. | Strict-string lookup (silent 20.00 for `'gold'`); treating a bad division as unranked (throws away a known tier) |
| 2026-09-08 | `rateGame` throws unless both sides have exactly five ratings | A League custom is 5v5 and the API only rates games with a full roster; an empty or short team makes OpenSkill produce nonsense quietly. Throwing keeps a malformed ingest out of the rating history. | Rating whatever arrives (silent bad data); padding a short side |
| 2026-09-08 | Tuning constants live in `config.rating.*` in `packages/core/src/config.ts`; M1.4 adds `config.balance.*` beside it | One object, namespaced per module, so a tuning change is a one-line diff plus a test update and consumers import a single `config`. | One flat object (name collisions once balance weights arrive); constants scattered per module |
| 2026-09-08 | The M1.3 convergence test rates P0's team against the next five players in the same rotation; the tenth player sits that game | The brief's setup is P0 plus ten others, so "the remaining five" is really six and `rateGame` rejects a 6-player side. Rotating the opponents keeps every game 5v5 and the sequence deterministic. Results reported to the lead, not tuned: `mu` passes 23.00 in game 4 and is 34.09 after game 10; `sigma` is 6.47 after game 10 and first drops below 5.00 in game 36. | Nine other players (changes the brief's numbers); relaxing `rateGame` to accept six |
| 2026-09-08 | The unions in the schema are Postgres enums (`lobby_status`, `player_role`, `game_source`, `companion_command_kind`, `companion_command_status`), not check constraints | `supabase gen types typescript` turns an enum into the same string union `packages/core` declares, so `LobbyRow['status']` is `'open' \| 'balanced' \| ...` and the state machine typechecks. A check constraint generates `string`. `side` stays a smallint with a check because 100/200 are the client's numbers, not a vocabulary of ours. | Check constraints everywhere (loses the union in the generated types); a `sides` lookup table |
| 2026-09-08 | `discord_id` is hidden with a `players_public` view; the `players` table itself is service-role only | Column-level grants make PostgREST's `select=*` fail outright for anon, which breaks every public page. A view with `security_invoker` off is the only shape that keeps `select=*` working and still returns `401 permission denied` for `discord_id`. Consequence for the web and bot: read `players_public`, never `players`. | Column grants on `players`; an RLS policy that cannot hide a column; keeping `discord_id` in a side table (an extra join on every page) |
| 2026-09-08 | `ratings.ordinal` is a stored generated column (`mu - 2 * sigma`) with an index on `(season_id, ordinal desc)` | The leaderboard has to sort in SQL, so the formula exists in the database whether we write it down or not; generating it means one definition instead of an expression index every query must match. `packages/core` stays the only place that *computes* a rating. | Expression index plus `order=mu-2*sigma` in every query; sorting in the app after fetching every row |
| 2026-09-08 | The first admin is `public.bootstrap_admin(puuid)`, an idempotent SQL function the API calls on start with `BOOTSTRAP_ADMIN_PUUID`, not a value baked into a migration | A migration cannot read Vercel's environment, and a hard-coded PUUID in applied SQL can never be changed. The function inserts the player if the PUUID is new and sets `is_admin` either way, so calling it on every boot is a no-op. Service role only. | A PUUID literal in `0001_init.sql`; a one-off admin script someone has to remember to run |
| 2026-09-08 | `0001_init.sql` inserts Season 1 (active, fixed id `00000000-...-0001`, exported as `SEASON_ONE_ID`) and `games.season_id` defaults to `public.active_season_id()` | Ratings and games are per season from the first row, so there must be a season before the first game; a fixed id makes local resets and tests deterministic and gives the API a default it never has to look up. | Creating the season by hand in Studio; nullable `season_id` until M5.3 |
| 2026-09-08 | `splits` gains `explanation`, `created_at` and `roster_key`, and a rebalance appends a new set of three rather than replacing the old one | The explanation is built in core and must not be recomputed by the tonight page or the reroll. `roster_key` (the ten puuids sorted and joined) is how the API finds "the last chosen split for these same ten" to pass as `lastSplit`, in one indexed lookup instead of a jsonb set comparison. A partial unique index keeps at most one `is_chosen` split per lobby. Deviation from `01-architecture.md` "Data model", which lists neither column. | Recomputing the explanation on read; comparing `blue`/`red` jsonb arrays to find the last split; unique `(lobby_id, rank)` (would forbid keeping the previous split as history) |
| 2026-09-08 | `companion_tokens` gains `revoked_at`; command statuses are `pending`, `sent`, `acked`, `failed` | Revoking by deleting the row throws away `last_seen_at` and the audit trail of a token that may have been leaked; a timestamp is a soft delete the auth path already filters on with a partial index. The four statuses are exactly the poll/execute/ack loop in M4.1 plus its failure. | Deleting the token row to revoke; a boolean `is_revoked` (no when); adding an `expired` status nothing sets |
| 2026-09-08 | `game_players.mu_before/sigma_before/mu_after/sigma_after` are nullable | The API inserts the game and its ten players, then rates: the rating columns are written a step later, and a rebuild (M5.2) overwrites them. Not-null would force one giant statement or a placeholder that lies. | Not null with a 0 placeholder; a separate `game_ratings` table |
| 2026-09-08 | `packages/db` integration tests hit PostgREST with `fetch` and the CLI's keys, and skip themselves when the local stack is unreachable | Testing through PostgREST is testing the path the API and the browser actually take, RLS and all, and it keeps `@supabase/supabase-js` out of this package's dependencies. Skipping (not failing) keeps `pnpm -r test` green on a machine without Docker. | `@supabase/supabase-js` in `packages/db`; direct `psql` (bypasses RLS and PostgREST, so it proves nothing about anon); no integration test at all |
| 2026-09-08 | Supabase Storage is disabled in the local `config.toml` | The project stores no files. Leaving it on also made `supabase db reset` exit 1 on a 502 from the Storage container's restart, which would have made a documented command fail for everyone. | Keeping Storage enabled and telling people to ignore the failure |
| 2026-09-08 | `0001_init.sql` adds `lobbies`, `lobby_members`, `splits`, `games`, `game_players` and `ratings` to the `supabase_realtime` publication | Supabase creates that publication empty, and a table that is not in it never emits a `postgres_changes` event — silently, with a subscription that looks healthy. The tonight page (M3.4) and the bot (M4.4) are built on those events, so publishing belongs in the migration that creates the tables. `players` is left out because it is not publicly readable. | Adding tables to the publication by hand in Studio (invisible, and lost on every `db reset`); polling instead of Realtime |
| 2026-09-08 | Balancer scores closer than `1e-9` display points are a tie and fall through to the next tie-break key (`offRoleCount`, then the sorted blue puuids) | Two partitions can have the same arithmetic gap but sum their five effective skills in a different order, and floating point then differs in the last bit. Without a tolerance the brief's tie-break would be decided by that noise instead of by the stated key. Real differences are at least 0.6 points (`mu` carries two decimals), so `1e-9` cannot merge two genuinely different scores. | Exact float comparison (tie-break silently driven by summation order); rounding scores before comparing (changes the number the explanation prints) |
| 2026-09-08 | A `roleOverride` on a flexible player (`mainRole: null`) makes the override their only main; every other role is fill and off-role for them tonight | Literal application of the override rule: the usual main becomes the backup, and a null usual main is no backup. The player tapped a role, so honouring it is the only outcome they would not call rigged. A flexible player who taps nothing stays flexible. | Ignoring the override for flexible players (they tap top, get support, and the line still says "everyone on a main role"); keeping every other role at 1.00 (same problem) |
| 2026-09-08 | Each side of a `Split` is listed in lane order: top, jungle, mid, adc, support | The Discord embed, the tonight page and the "off-role" clause all read in lane order, so storing it that way means nobody sorts twice and the stored shape matches the printed one. Determinism does not depend on it (the sorted puuid list is the tie-break key), it is purely the shape consumers get. | Puuid order (the enumeration order, meaningless to a reader) |
| 2026-09-08 | `explain(split, next, players)` is exported from `@customs/core` beside `balance`, and `balance` builds its `explanations` with that same function | One code path for the sentence, so the string stored in the `splits` table and any string recomputed later (rebuilds, tests, a future copy change) cannot drift apart. `players` supplies names and role settings; the split itself carries no names because names get renamed and puuids do not. | Explanation built privately inside `balance` only (tests would have to reach around the API to check the aligned-side logic); storing names in the split |
| 2026-09-08 | `players_public` keeps `is_admin`; only `discord_id` is withheld | Who can press reroll is not a secret from the group, and the tonight page needs the flag to decide whether to draw the reroll button. Reading it from the public view keeps that page on the anon key instead of adding a service-role call to a public page. | Dropping `is_admin` from the view (the tonight page then needs a privileged round trip just to show or hide a button); exposing the whole `players` row (leaks `discord_id`) |
| 2026-09-08 | `packages/lcu` TLS default is `pinned`: verify the chain against the vendored `certs/riotgames.pem` only, with hostname verification skipped because the peer is always 127.0.0.1. `legacyDigests` (OpenSSL `SECLEVEL=0`, for a SHA-1 signed leaf) and `insecure` (`rejectUnauthorized: false`) are explicit opt-ins; the smoke script probes the three in that order and reports which worked | Pinning is nearly free and turns "anything on loopback" into "Riot-signed on loopback". Hostname checks cannot be kept until M0.2 shows what SAN the leaf carries, and a synthetic chain showed Node accepts a SHA-1 root but not a SHA-1 leaf at the default level, so the fallback ladder has to be in the code before the first live run | `rejectUnauthorized: false` as the default (the documented fallback; kept as the last rung); pinning with hostname checks on (would fail if the leaf has no `127.0.0.1` SAN) |
| 2026-09-08 | Fixtures are envelopes: `{ id, method, path, status, capturedAt, patch, clientVersion, contentType, body | bodyText }` under `fixtures/<major.minor>/<endpoint-id>.json`, with `body` the raw JSON untouched | A 404 for `lobby` and a non-JSON reply are data too, and M0.3 schemas need the status next to the body. `major.minor` matches how Riot names patches | Raw body only (loses the status; a 404 body looks like a real response); full version as the directory name (one directory per hotfix) |
| 2026-09-08 | `LcuClient` never throws for anything the client does: results are `{ ok: true, status, json }` or `{ ok: false, reason: 'http' \| 'malformed' \| 'schema' \| 'network' }`, each logged with `METHOD path`. `LcuSocket` remembers subscriptions and re-sends them on every `connect()`, rejects `connect()` only before the socket opened, and afterwards reports everything as `close`/`dropped` events; it has no backoff (M2.1 owns the loop) | The companion must survive a patch restart, a sleeping PC and a malformed frame without a single uncaught path; making the failure a value forces every caller to handle it | Throwing typed errors (one forgotten `try` crashes the watcher); putting backoff inside the socket (hides the policy the companion needs to log and tune) |
| 2026-09-08 | `packages/lcu` scripts (`smoke`, `record-ws`) run through `tsx`, pinned as a dev dependency | Relative imports use `.js` per the repo convention and Node's built-in type stripping does not map `.js` to `.ts`; `tsx` does, and there is still no build step | Node `--experimental-strip-types` (import specifiers would have to become `.ts`); a `dist` build for scripts only |
| 2026-09-08 | Every League client path lives in `packages/lcu/src/endpoints.ts` (`READ_ENDPOINTS`, `WRITE_ENDPOINTS`, `LIVE_CLIENT_DATA`); the smoke script walks that catalogue rather than its own list | The catalogue and the reference-doc table drift otherwise, and "the post-patch check hits every endpoint we use" is only true if there is exactly one list | Paths inline where they are called |
| 2026-09-08 | Recorded WebSocket events are scrubbed by URI deny-list plus key deny-list before they are written: `/lol-login`, `/lol-rso-auth`, `/riotclient/auth`, `/lol-chat` and any URI containing auth/token/credential/password/secret are written as `{ ts, topic, uri, eventType, redacted: true }` with no `data`; inside every other payload, keys matching token/password/secret/cookie/authorization/credential/jwt/bearer become `[redacted]`. Frames the parser refused get the same treatment (`{ ts, reason, dropped: true, redacted: true, uri }` for a sensitive URI, a key-scrubbed `frame` otherwise, and a 200-character text-scrubbed `preview` when the frame is not JSON), never the raw text. The reader of `ws-events.ndjson` therefore always sees which events fired, never a credential | `OnJsonApiEvent` includes the login session (`idToken`) and RSO access/refresh tokens, and `fixtures/` is committed. Redacting `data` instead of dropping the event keeps the event-order evidence M0.3 needs (which URIs fire around EndOfGame) | Dropping sensitive events entirely (loses the timeline); trusting the reviewer to skim the file before committing (the README still asks for that, as a second line) |
| 2026-09-08 | The smoke TLS probe steps down only on a TLS error (`isTlsError`); ECONNREFUSED/ETIMEDOUT stop it with exit 3 | Otherwise a client that is still starting would time out on pinned modes, answer on insecure, and the manifest would falsely record that pinning fails, corrupting the answer to reference question 8 | Stepping down on any network failure (simpler, dishonest) |
| 2026-09-08 | `checkServerIdentity` is skipped for `127.0.0.1` only; any other `host` gets Node's normal hostname check | `LcuClient`/`LcuSocket` accept a `host` for tests; a blanket skip would silently weaken TLS for whoever passes a real hostname later | Blanket skip (original M0.1 draft); removing the `host` option (tests need it for the localhost case) |
| 2026-09-08 | Relative imports drop the `.js` extension (`from './types'`, not `'./types.js'`) in every package `apps/web` imports — that is `packages/core` and `packages/db`. `packages/lcu` is deliberately exempt: the web app must never import it, and its scripts run through `tsx`, which does map `.js` to `.ts` (see the `tsx` row above) | Turbopack has no `extensionAlias`, so it cannot resolve a `./x.js` specifier to `x.ts`. `next build` and `next dev` both failed on `apps/web/app/page.tsx` importing `@customs/core` — the whole app was 500 before M1.5 touched it, and every route that imports `@customs/db/schemas` would have been too. With source-shipping packages and `moduleResolution: "Bundler"`, extensionless is the specifier every consumer of core and db (tsc, vitest, Turbopack) agrees on. | `experimental.extensionAlias` (webpack only, Next 16 defaults to Turbopack); `next build --webpack` (deprecated path, and dev would still need the flag); building packages to `dist` (already rejected: breaks a fresh checkout); applying the rule to `lcu` too (churn in a package no bundler ever sees) |
| 2026-09-08 | Companion auth is a handler wrapper, `withCompanionAuth(schema, handler)`, not Next middleware; it authenticates before it parses the body | Middleware cannot be unit tested without a server and would hand the handler a header to re-read instead of a typed identity. Authenticating first means an unauthenticated caller learns nothing about the payload shape we expect. | Next middleware on `/api/companion/*`; a `requireCompanion(request)` call at the top of every handler (easy to forget) |
| 2026-09-08 | `companion_tokens.last_seen_at` is written at most once every 5 minutes per token | The companion polls; writing a timestamp on every request would be one write per poll for a field only a human reads on the admin page. The lookup already returns `last_seen_at`, so the throttle costs nothing. | Writing on every request; not tracking `last_seen_at` at all (an admin needs to see which companions are alive) |
| 2026-09-08 | `bootstrap_admin` runs lazily on the first companion request of a process, memoised, and never fails the request | A build-time or cold-start hook (`instrumentation.ts`) would have to cope with the database being unreachable during `next build`, and nothing needs the admin row to exist before the first request. The SQL function is idempotent, so "once per process" is a cost optimisation, not a correctness rule. | `instrumentation.ts register()`; calling it from a migration (cannot read the environment); a script someone has to remember to run |
| 2026-09-08 | `POST /api/companion/rank` accepts any PUUID from any valid token, and only a `RANKED_SOLO_5x5` payload writes the rank columns | The companion reports the rank of unknown lobby members so a first-time player can be seeded before their first game (M2.4), so restricting it to the token's own player would break seeding. A rank is a lookup the client performed, not a claim about who the caller is. One player row holds one rank, and the seed table is a solo-queue table, so a flex reading must not overwrite it; it is accepted and reported as `stored: false`. | Only the token's own PUUID (kills M2.4 seeding); storing whichever queue arrived last (a flex rank would silently reseed a player) |
| 2026-09-08 | An end-of-game block whose `gameType` is missing, null or anything but `CUSTOM_GAME` is refused with 422 | The companion reads `gameType` straight off the block, so its absence means we are looking at something we do not understand — and a ranked game landing in the customs ratings is worse than a dropped game we can backfill. | Ingesting when `gameType` is absent (optimistic); accepting and flagging the row for later |
| 2026-09-08 | Ingest diffs before it writes: a repeated identical lobby or player post updates no column at all | `lobbies.updated_at` has a trigger, so a blind upsert would bump it on every poll and "updated" would stop meaning "something changed" — which M2.5's stability rule and the tonight page both read. It also makes "post the same lobby twice, nothing changes" literally true rather than true of row counts only. | Blind upsert on every post; comparing in SQL with a `WHERE ... IS DISTINCT FROM` clause per column (PostgREST cannot express it) |
