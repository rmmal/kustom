# League Client (LCU) reference

The League client runs a local HTTPS server with a self-signed certificate and a WebSocket event stream. This is
the only data source for the project. It is unofficial: endpoints can change on any patch. Everything that talks
to it lives in `packages/lcu`.

**Status column:** `verified` means exercised against a live client on the listed patch and the response shape is
pinned in a zod schema plus a fixture in `packages/lcu/fixtures/`. `unverified` means from memory or community
docs. **M0 exists to turn every row we need for M2 to `verified`.** Do not build on an unverified row.

## Connecting

| Item | Detail | Status |
|---|---|---|
| Lockfile | `<install dir>/lockfile`, content `LeagueClient:<pid>:<port>:<password>:https`. Default install `C:\Riot Games\League of Legends\lockfile` on Windows, `/Applications/League of Legends.app/Contents/LoL/lockfile` on macOS. M0 can run on a Mac with League installed; packaging targets Windows. Evidence so far (2026-09-08, client 16.17.812.4632, not yet read while running): this Mac's `LeagueClient.log` says the client is `Running from cwd '/Applications/League of Legends.app/Contents/LoL'`, which is where the lockfile is written. `discoverLockfile` in `packages/lcu` tries a configured override, then `LCU_LOCKFILE_CANDIDATES` (path-delimiter-separated list, replaces the defaults; tests set it so a running client is invisible), then the platform default. Verified 2026-09-08 on macOS with the client running: the default path existed, parsed as `LeagueClient:86388:50844:<password>:https`, and the pid was the running `LeagueClient` process. Windows default not yet run. | verified (16.17, 2026-09-08) (macOS) |
| Process args fallback | On Windows, the `LeagueClientUx.exe` command line contains `--app-port=` and `--remoting-auth-token=`. Use when the install dir is unknown. Also present on macOS: this Mac's `LeagueClientUx.log` (2026-09-08) shows `--app-port=60969` on the Ux command line, distinct from the Riot Client's `--riotclient-app-port`. Confirmed again 2026-09-08 on the running macOS client: `LeagueClientUx` carries `--app-port=<port>` and `--remoting-auth-token=<password>` matching the lockfile exactly. Not implemented yet (M2). | unverified (observed, no code) |
| Auth | HTTP Basic, user `riot`, password from lockfile. Accept the self-signed cert (pin Riot's root, `riotgames.pem`, if practical; otherwise `rejectUnauthorized: false` on loopback only). Riot's root is vendored at `packages/lcu/certs/riotgames.pem` (fetched from `static.developer.riotgames.com/docs/lol/riotgames.pem`, SHA-256 fingerprint in `certs/README.md`). It is SHA-1 self-signed; Node's default OpenSSL level accepts that for a trust anchor (checked locally with a synthetic chain) but rejects a SHA-1 signed *leaf*, which `{ mode: 'pinned', legacyDigests: true }` (`DEFAULT@SECLEVEL=0`) allows. **Answer (16.17, 2026-09-08, macOS): plain `pinned` (Riot's root, default security level, no legacy digests) answered HTTP 200 on the first attempt for both HTTPS and the WebSocket.** Neither `legacyDigests` nor `insecure` was needed. `smoke` still probes pinned, pinned+legacy, insecure in that order and prints which one answered, so a future patch that rotates the certificate is visible. Companion default is `pinned`. | verified (16.17, 2026-09-08) |
| WebSocket | `wss://127.0.0.1:<port>` with the same basic auth. Send `[5, "OnJsonApiEvent"]` to subscribe to everything, or `[5, "OnJsonApiEvent_lol-lobby_v2_lobby"]` for one URI. Messages are `[8, "OnJsonApiEvent...", { data, eventType: "Create"|"Update"|"Delete", uri }]`. `[6, topic]` unsubscribes. Subprotocol: `packages/lcu` offers none by default (some community Node clients offer `wamp`; the Python ones offer nothing); `record-ws` prints what the server negotiated. Verified 16.17 (2026-09-08): `[5, "OnJsonApiEvent"]` subscribes, the server negotiated no subprotocol (`protocol: ""`), events arrive as `[8, "OnJsonApiEvent", { data, eventType, uri }]` with `eventType` `Create`/`Update`/`Delete` (`Delete` carries `data: null`), and `parseFrame` accepted every frame: 1310 events over 21 minutes across two custom games, 0 malformed. Two recorders (the user's and this worktree's) on the same client saw the same events. Recording in `fixtures/16.17/ws-events.ndjson`, trimmed to the URIs the companion reads (see fixtures/README.md). The empty frame after subscribe is real: on 16.17 (2026-09-08, companion live run) the client sent one empty frame within 2 ms of `[5, "OnJsonApiEvent"]`; `LcuSocket` logs it at debug as `lcu socket empty frame` and drops it, so nothing needs to change. | verified (16.17, 2026-09-08) |

## Tooling (`packages/lcu`, M0.1)

- `pnpm --filter @customs/lcu smoke` finds the lockfile, probes the TLS modes, reads the version, then GETs every row in
  "Endpoints we use" (read-only ones; path parameters are filled from `current-summoner` and the first
  `CUSTOM_GAME` in the local player's match history) and writes `packages/lcu/fixtures/<patch>/<endpoint-id>.json`
  plus `manifest.json`. Exit 2: no lockfile. Exit 3: lockfile present but no TLS mode reached the client.
  `--diff` compares fresh top-level key sets and statuses with the newest saved fixtures instead of writing
  (exit 1 when anything differs). `--puuid <puuid>` and `--riot-id Name#TAG` add probes for another player
  (question 4 below). `--insecure` skips pinning. `--game-id <id>` pins the match-detail probe (the list cannot tell a 5v5
  from a solo abort). `--live-port` redirects the in-game live data probe (tests point it at a dead port).
  Bodies are scrubbed like WS events before they are written (`scrubValue`); the table says when something was
  redacted. Layout in `packages/lcu/fixtures/README.md`. `LCU_LOCKFILE_CANDIDATES` (path-delimiter-separated) replaces the platform default lockfile paths; the unit tests set it to a non-existent path so a client running on the developer's machine never leaks into a test.
- `src/schemas.ts` holds one zod schema per verified row, written from the 16.17 fixtures and parsed against them in `src/schemas.test.ts` (fixtures only, never a live client). Tolerant on unknown keys, exact on the fields we read.
- `pnpm --filter @customs/lcu record-ws` subscribes to `OnJsonApiEvent` (or `--topic` ones) and appends every
  event to `fixtures/<patch>/ws-events.ndjson` until Ctrl-C, reconnecting if the client restarts. On exit it
  prints a count per URI. Events are scrubbed before they touch disk (`src/scrub.ts`): `/lol-login`,
  `/lol-rso-auth`, `/riotclient/auth`, `/lol-chat` and any URI mentioning auth/token are written without
  `data`; credential-looking keys elsewhere become `[redacted]`. The summary says how many were redacted.
- The TLS probe only steps down from `pinned` to `pinned+legacy` to `insecure` on a certificate/handshake
  error. A refused or timed-out connection stops the probe (exit 3) so a client that is still starting is
  never recorded as "needed insecure".
- Both scripts are GET-only. Nothing in M0.1 creates a lobby, invites, or sends anything but subscribe frames.

## Behaviors to confirm in M0

1. Custom games in match history: **yes** (16.17, 2026-09-08: 17 of 21 games in the default window were `CUSTOM_GAME`, spanning four days of play). The default window is 21 games (`begIndex=0&endIndex=20`, inclusive); the user's first run saw 16 customs, later runs 17, so the window slides. Paging further back (`begIndex` > 20) is still untested. **The list holds only the local player per game; use match detail for rosters.**
2. Does `eog-stats-block` persist after the player clicks past the end-of-game screen? **It persists while the screen is up (GET 200 at +33 s and +4 min) and is gone (404) once the client is back in the lobby (+10 min).** The exact moment it is deleted was not captured (the `Delete` event for the played game fell outside both recordings; the server-dropped game got a `Delete` 0.2 s after `Create`). So: the companion reacts to the WS `Create`/`Update` event (which arrives before the phase even reaches `EndOfGame`) and keeps the block in memory; a GET on `EndOfGame` is a fallback, and polling later is not (16.17, 2026-09-08).
3. Does `lobby.members[].teamId` reflect sides in a custom lobby, or only `gameConfig.customTeam100/200`? **Only `gameConfig.customTeam100/200`.** `members[].teamId` and `localMember.teamId` stayed `0` while the local player switched from blue to red and back (WS events 16:33:26-16:33:31). Confirmed with a real second human (second window, 17:31:58-17:32:08): the friend's `teamId` was `0` on join (placed on `customTeam200`), while on `customTeam100`, and after moving back. **Join order for side derivation:** the first `/lol-lobby/v2/lobby` `Update` that listed the friend in `members[]` listed them in `customTeam200[]` in the same payload; there was no event with the member in one and not the other, and across all 39 lobby events of both windows the human puuids of `members[]` equal the union of the three side arrays. The `/lol-lobby/v2/lobby/members` event followed 2 ms after that `Update`. So M2.2 can derive every member's side from the lobby event it arrives in and never has to wait for a later one. **Spectators (third window, 17:38:57-17:39:27): a spectator is in `members[]` with `isSpectator: true` *and* in `customSpectators[]`, on neither team, `teamId` still `0`** (question 9 has the timestamps). Side derivation for M2.2: `customTeam100` -> 100, `customTeam200` -> 200, `customSpectators` -> spectator (`side: null`), and every human in `members[]` is in exactly one of the three. Tested in `schemas.test.ts` (16.17, 2026-09-08).
4. `ranked-stats/{puuid}` for another player: **works for a non-friend and a friend alike** (16.17, 2026-09-08). `losses` reads 0 for others.
5. Switch-side endpoint path and whether it works when the target side is full. **Open**: read-only capture cannot answer it. Next step (M4.3): with a custom lobby open, `POST /lol-lobby/v1/lobby/custom/switch-teams` with an empty body, then the v2 path if v1 is 404, and watch `gameConfig.customTeam100/200` in the lobby event; then fill the target side with bots and retry.
6. Invite by `summonerId` still works, or is `puuid` required now? **Open**: read-only capture cannot answer it. The two invites in the second capture were sent from the client UI by the user, not by our POST, so the endpoint stays unverified; what they show is the *result* shape: `invitations[]` gets a `Pending` row carrying both `toPuuid` and `toSummonerId` (with `invitationId: ""` and `invitationType: "invalid"`, so neither is an id to track), and it becomes `Accepted` in the same `Update` that adds the member. Next step (M4.2): `POST /lol-lobby/v2/lobby/invitations` with `[{ "toSummonerId": <id> }]` for a friend's `summonerId` from `summoner-by-puuid`; if it 4xx's, retry with `[{ "toPuuid": "<puuid>" }]`; compare the resulting `invitations[]` row with the UI-sent ones in `lobby--two-players.json`.
7. WebSocket event names and whether the `[5, ...]` subscription format is unchanged: **unchanged** (16.17, 2026-09-08; `[5, "OnJsonApiEvent"]` -> `[8, "OnJsonApiEvent", { data, eventType, uri }]`, no subprotocol, 1310 events, 0 malformed). ## Riot policy notes

- The LCU is not an official API. Riot tolerates read and lobby automation and explicitly forbids automating
  gameplay. Register the project in the Riot developer portal as a personal app that uses the LCU; it is free and
  is what Riot asks.
- Vanguard does not interfere with local API reads (16.17: every read and the WebSocket worked with Vanguard running).
- The event stream also carries `/lol-champ-select/*`, `/lol-lobby-team-builder/champ-select/*` and `/lol-matchmaking/*` events with full payloads. They are recorded because we subscribe to everything; the companion must never act on them, subscribe to them on purpose, or POST to those paths. That is the gameplay line.
- `/riot-messaging-service/*` is server push the companion never reads. Its `lol-gsm-server` `game-update` messages carry the player's game credentials (`encryptionKey`, `spectatorKey`, `observerEncryptionKey`, `packetCopMetadata`, server ip and port) inside a JSON *string* (`payload`), a second delivery of `/lol-gameflow/v1/player-credentials`. `scrub.ts` treats the whole prefix as sensitive and, since 2026-09-08, parses JSON strings before key-scrubbing so that path cannot leak again.
- Do not display other players' custom match history publicly beyond our own group's site. Keep the site unlisted.
